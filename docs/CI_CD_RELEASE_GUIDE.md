# CI/CD Release System Guide

## Problem Solved

The issue was that GitHub Actions workflows were not automatically triggered when `stable` and `beta` tags were created, so the release .zip files were not being built and uploaded automatically.

## Implemented Solution

The workflows have been updated to support custom tags:

### 1. **Tagged Release** (`.github/workflows/tagged-release.yml`)
- **Trigger**: Activates when a `v*` or `stable` tag is created
- **Output**: Creates an `Onion-v{VERSION}.zip` file as a draft release
- **Behavior**:
  - For `v*` tags: uses version from tag (e.g., `v4.3.1` → version `4.3.1`)
  - For `stable` tag: uses version from Makefile

### 2. **Pre-release** (`.github/workflows/pre-release.yml`)
- **Trigger**: Manually via workflow_dispatch (GitHub Actions UI)
- **Output**: Creates an `Onion-v{VERSION}-{SHA}.zip` file as a pre-release
- **Behavior**:
  - Uses version from Makefile + current commit SHA (from `HEAD`)

## How to Use

### To Create a Stable Release

1. **Update the version** in `Makefile` if needed
2. **Create and push the `stable` tag**:
   ```bash
   git tag -f stable
   git push -f origin stable
   ```
3. The `tagged-release` workflow will automatically:
   - Build the project
   - Create the `Onion-v{VERSION}.zip` file
   - Upload it to the release with tag `stable` (as draft)

### To Create a Beta Release

1. **Update the version** in `Makefile` if needed (format: `X.Y.Z-beta-DD_MM_YYYY`)
2. **Go to GitHub → Actions** and select the "Pre-release" workflow
3. Click **"Run workflow"**, select the branch, and click **"Run workflow"**
4. The `pre-release` workflow will automatically:
   - Build the project
   - Create the `Onion-v{VERSION}-{SHA}.zip` file
   - Upload it to the release with tag `latest` (as pre-release)

### For Version-Specific Releases

You can still use the traditional format with `v*` tags:
```bash
git tag v4.4.0
git push origin v4.4.0
```

This will create a draft release with the file `Onion-v4.4.0.zip`.

## The Three .zip Files in a Release

When the workflow works correctly, you'll see **three .zip files** on the release page:

1. **`Onion-v{VERSION}.zip` or `Onion-v{VERSION}-{SHA}.zip`**
   - The main file built by the workflow
   - Contains the entire Onion distribution

2. **`Source code (zip)`**
   - Automatically generated by GitHub
   - Contains the source code at the time of the tag

3. **`Source code (tar.gz)`**
   - Automatically generated by GitHub
   - Same as #2, but in tar.gz format

## Important Notes

- **Don't manually upload** .zip files to releases - let the workflows do it automatically
- If you've already manually uploaded files, you can **delete them** and recreate the tag to restart the workflow
- Workflows require that **submodules are properly initialized**
- To **force a rebuild**, you can delete and recreate the tag:
  ```bash
  git tag -d stable          # delete locally
  git push origin :stable    # delete on GitHub
  git tag stable             # create again
  git push origin stable     # push again
  ```

## Workflow Verification

After pushing a tag, you can verify the workflow status:

1. Go to GitHub → Actions
2. Look for the "Tagged release" or "Pre-release" workflow
3. Check that it's running and completes successfully
4. Verify that the .zip file has been uploaded to the release

## Troubleshooting

### Workflow doesn't trigger
- Verify the tag was pushed correctly: `git ls-remote --tags origin`
- Check that the workflow file has no syntax errors

### Workflow fails during build
- Check the workflow logs on GitHub Actions
- Verify that submodules are initialized
- Ensure the version in Makefile is valid

### .zip file is not uploaded
- Verify that the build completed successfully
- Check that the file exists in `release/` after build
- Verify GITHUB_TOKEN permissions
