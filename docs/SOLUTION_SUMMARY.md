# CI/CD Solution Summary for Automatic Releases

## Original Problem

The user (Amiga500) had manually uploaded a beta and a stable build to the fork repository, but was not seeing "the third .zip file" as on OnionUI/Onion. The problem was related to the GitHub Actions CI/CD system.

## Root Cause

The GitHub Actions workflows were not triggering automatically for the `stable` and `beta` tags because:

1. **`tagged-release.yml`** only triggered for tags starting with `v*` (e.g. `v4.3.1`)
2. **`pre-release.yml`** only triggered manually via `workflow_dispatch` or for commits on specific branches (commented out)
3. The `stable` and `beta` tags used by the user did not match any of these patterns

Therefore, when the user created or updated these tags, the workflows did not run and the .zip files were not built/uploaded automatically.

## Implemented Solution

### 1. Update of `tagged-release.yml`
**File**: `.github/workflows/tagged-release.yml`

**Changes**:
- Added trigger for the `stable` tag
- Improved version extraction logic:
  - For `stable` tag: uses the version from the Makefile
  - For `v*` tags: continues to use the version from the tag name

**Behavior**:
- When the `stable` tag is pushed, the workflow:
  1. Checks out the code with submodules
  2. Extracts the version from the Makefile
  3. Builds the project with `make release`
  4. Creates a draft release with the `Onion-v{VERSION}.zip` file

### 2. Update of `pre-release.yml`
**File**: `.github/workflows/pre-release.yml`

**Changes**:
- Added trigger for the `beta` tag
- Improved SHA extraction logic:
  - For `beta` tag: uses the current commit SHA
  - For manual workflow_dispatch: uses the SHA from origin/main
- Added separate step to determine the release tag:
  - For `beta` tag: uses `beta` as the release tag
  - For other cases: uses `latest` as the release tag

**Behavior**:
- When the `beta` tag is pushed, the workflow:
  1. Checks out the code with submodules
  2. Extracts the version from the Makefile and the current SHA
  3. Builds the project with `make release`
  4. Creates a pre-release with the `Onion-v{VERSION}-{SHA}.zip` file using the `beta` tag

## The Three .zip Files

When the workflows work correctly, each GitHub release contains **three .zip files**:

1. **`Onion-v{VERSION}.zip`** or **`Onion-v{VERSION}-{SHA}.zip`**
   - Main file built by the GitHub Actions workflow
   - Contains the entire ready-to-use Onion distribution
   - This is the file users need to download and install

2. **`Source code (zip)`**
   - Automatically generated by GitHub for each release/tag
   - Contains the complete source code at the time of the tag
   - Useful for developers who want to build from source

3. **`Source code (tar.gz)`**
   - Automatically generated by GitHub for each release/tag
   - Same content as file #2, but in tar.gz format instead of zip
   - Preferred on Unix/Linux systems

Before this fix, the user only saw the manually uploaded files, without the three standard files that appear when the workflows run correctly.

## How to Use the Solution

### For Stable Releases
```bash
# Make sure the version in the Makefile is correct
# Then create/update the stable tag
git tag -f stable
git push -f origin stable
```

The `tagged-release` workflow will trigger automatically and create the release.

### For Beta Releases
```bash
# Make sure changes are committed
# Then create/update the beta tag
git tag -f beta
git push -f origin beta
```

The `pre-release` workflow will trigger automatically and create the pre-release.

## Benefits of the Solution

1. **Full Automation**: No longer necessary to manually build and upload .zip files
2. **Consistency**: Every release is built in the same standardized Docker environment
3. **Traceability**: Every build is linked to a specific commit (via SHA for beta)
4. **Flexibility**: Supports both semantic tags (`v*`) and symbolic tags (`stable`, `beta`)
5. **Compatibility**: Maintains backward compatibility with the existing OnionUI/Onion system
